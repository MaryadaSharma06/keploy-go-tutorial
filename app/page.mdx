<Callout type="info" title="How this tutorial works">

Keploy observes real API traffic from your Go application, records the request and response, captures the required database interactions, and turns them into reusable test cases.

</Callout>

## What you'll learn

 

By the end of this tutorial, you'll know how to:

 

- Start the Go application with PostgreSQL

- Verify that the API is working before using Keploy

- Record real API interactions with Keploy

- Generate HTTP test cases and PostgreSQL mocks

- Replay recorded test cases

- Inspect Keploy-generated artifacts and reports

- Understand what Keploy is doing behind the scenes

- Troubleshoot common setup problems

 

---

 

<h2 id="prerequisites">Prerequisites</h2>

 

Before starting, make sure you have:

 

- Go installed

- Docker installed and running

- A WSL/Linux environment

- Keploy installed

- `curl` available

- The Go sample application available locally

 

<Callout type="tip" title="Why start with the application first?">

Keploy records interactions with a running application. If the API or its database is not working before recording starts, the generated test cases will not represent a healthy application flow.

</Callout>

 

---

 

<h2 id="start-postgresql">Step 1 — Start PostgreSQL</h2>

 

<Step number="1" title="Start PostgreSQL">

 

Move into the Go sample application:

 

<Command title="Terminal">

 

```bash

cd ~/samples-go/echo-sql

```

 

</Command>

 

The sample uses PostgreSQL as its database. Start the PostgreSQL service defined by the project's Docker Compose configuration:

 

<Command title="Terminal">

 

```bash

docker compose up -d postgres

```

 

</Command>

 

Check that the container is running:

 

<Command title="Terminal">

 

```bash

docker compose ps

```

 

</Command>

 

Look for the PostgreSQL container with a running or healthy status.

 

<Callout type="info" title="If PostgreSQL is already running">

Do not start a second PostgreSQL container. If `docker compose ps` already shows the database running and healthy, continue to the next step.

</Callout>

 

</Step>

 

---

 

<h2 id="verify-api">Step 2 — Verify the API</h2>

 

<Step number="2" title="Verify the API">

 

Before recording anything with Keploy, make sure the Go API itself works.

 

Build the application:

 

<Command title="Terminal">

 

```bash

go build -cover -o echo-psql-url-shortener .

```

 

</Command>

 

Start the application:

 

<Command title="Terminal">

 

```bash

./echo-psql-url-shortener

```

 

</Command>

 

Keep this terminal running.

 

Open a second terminal and send a request to the API:

 

<Command title="Second terminal">

 

```bash

curl http://localhost:8082

```

 

</Command>

 

The exact response depends on the sample application, but the important point is that the server should accept the request instead of returning a connection error.

 

<Callout type="success" title="Checkpoint">

If the API responds successfully, the application is ready for Keploy recording.

</Callout>

 

<Callout type="warning" title="Connection refused?">

Make sure the Go application is still running and that you are using the port configured by the sample.

</Callout>

 

</Step>

 

---

 

<h2 id="record">Step 3 — Record with Keploy</h2>

 

<Step number="3" title="Record real API interactions">

 

Move into the application directory:

 

<Command title="Terminal">

 

```bash

cd ~/samples-go/echo-sql

```

</Command> 

Start Keploy recording around the application:

 

<Command title="Terminal">

 

```bash

keploy record -c "./echo-psql-url-shortener"

```

 

</Command>

 

Leave the recording process running.

 

In another terminal, send real API requests.

 

Create a shortened URL:

 

<Command title="Terminal">

 

```bash

curl -X POST http://localhost:8082/url \

  -H "Content-Type: application/json" \

  -d '{"url":"https://example.com"}'

```

 

</Command>

 

You can also send a GET request using the short ID returned by the API:

 

<Command title="Terminal">

 

```bash

curl http://localhost:8082/<short-id>

```

 

</Command>

 

When you have finished recording, stop the Keploy process:

 

<Command title="Terminal">

 

```text

Ctrl+C

```

 

</Command>

 

Keploy stores generated test cases and mocks inside the `keploy/` directory.

 

<Callout type="success" title="What Keploy captured">

The recording can contain HTTP requests and responses as well as external interactions such as PostgreSQL calls required to reproduce the API behavior.

</Callout>

 

</Step>

 

---

 

<h2 id="test">Step 4 — Replay the tests</h2>

 

<Step number="4" title="Replay recorded tests">

 

Make sure PostgreSQL is running:

 

<Command title="Terminal">

 

```bash

docker compose up -d postgres

```

 

</Command>

 

Run the Keploy tests:

 

<Command title="Terminal">

 

```bash

keploy test -c "./echo-psql-url-shortener"

```

 

</Command>

 

Keploy replays the recorded requests and compares the observed responses with the recorded behavior.

 

<Callout type="success" title="A passing replay">

A successful test run means the recorded interaction could be reproduced by the application under test.

</Callout>

 

<Callout type="info" title="Why replay instead of manually repeating curl commands?">

The recorded test becomes a reusable regression test. You can run the same interaction again after changing the application without manually recreating the entire request sequence.

</Callout>

 

</Step>

 

---

 

<h2 id="inspect">Step 5 — Inspect the generated artifacts</h2>

 

<Step number="5" title="Inspect Keploy artifacts">

 

Inspect the generated `keploy` directory:

 

<Command title="Terminal">

 

```bash

find keploy -maxdepth 3 -type f | sort

```

 

</Command>

 

You should see files and directories similar to:

 

```text

keploy/

├── test-set-1/

│   ├── config.yaml

│   ├── mappings.yaml

│   ├── mocks.yaml

│   └── tests/

├── test-set-2/

│   ├── config.yaml

│   ├── mappings.yaml

│   ├── mocks.yaml

│   └── tests/

└── reports/

```

 

The exact filenames and number of test sets can differ depending on the interactions you recorded.

 

<InfoCard

  icon="📁"

  title="What are these files?"

  description="Test YAML files describe recorded HTTP interactions. Mock files contain captured external dependencies such as database interactions. Reports contain the results of replayed tests."

/>

 

</Step>

 

---

 

<h2 id="coverage">Step 6 — Understand the coverage report</h2>

 

<Step number="6" title="Understand the coverage report">

 

Inspect the reports:

 

<Command title="Terminal">

 

```bash

find keploy/reports -type f | sort

```

 

</Command>

 

You may see files such as:

 

```text

keploy/reports/test-run-0/coverage.yaml

keploy/reports/test-run-0/test-set-1-report.yaml

```

 

The report helps you understand what happened during the replayed test run.

 

<Callout type="info" title="Coverage is not the same as correctness">

Code coverage tells you which code was exercised. A high coverage value does not automatically mean that every behavior is tested correctly. Keploy's recorded request/response tests add another layer by checking actual API behavior.

</Callout>

 

</Step>

<h2 id="behind-the-scenes">Step 7 — Behind the scenes</h2>

 

<Step number="7" title="What Keploy is doing">

 

<Diagram

  title="From API request to automated test"

  items={[

    { icon: "⚙️", title: "Go API", text: "Your application" },

    { icon: "👀", title: "Keploy", text: "Observes traffic" },

    { icon: "🧪", title: "Test Case", text: "Stores request + response" },

    { icon: "🔁", title: "Replay", text: "Runs the interaction again" }

  ]}

/>

 

### 1. Your Go application receives a request

 

A client sends an HTTP request to the API.

 

### 2. Keploy observes the interaction

 

During recording, Keploy observes the application's interaction with external dependencies.

 

### 3. Keploy creates reusable test data

 

The request and response are converted into a test case. External dependency interactions can be stored as mocks.

 

### 4. The test is replayed

 

During testing, Keploy sends the recorded request to the application again and checks the resulting behavior.

 

<Callout type="tip" title="The key idea">

Instead of manually writing every integration test from scratch, you can turn real API interactions into reusable regression tests.

</Callout>

 

<InfoCard

  icon="💡"

  title="Why this matters for a Go developer"

  description="You can validate real application behavior, including interactions with external dependencies, without having to manually recreate every integration scenario."

/>

 

</Step>

<h2 id="troubleshooting">Troubleshooting</h2>

 

<Callout type="warning" title="PostgreSQL is not running">

 

Check Docker:

 

<Command title="Terminal">

 

```bash

docker compose ps

```

 

</Command>

 

If the PostgreSQL service is stopped:

 

<Command title="Terminal">

 

```bash

docker compose up -d postgres

```

 

</Command>

 

</Callout>

 

<Callout type="warning" title="API connection refused">

 

Check whether the Go process is running:

 

<Command title="Terminal">

 

```bash

ps aux | grep echo-psql-url-shortener

```

 

</Command>

 

Also confirm the port:

 

<Command title="Terminal">

 

```bash

curl http://localhost:8082

```

 

</Command>

 

</Callout>

 

<Callout type="warning" title="Keploy command not found">

 

Check that Keploy is installed and available in your PATH:

 

<Command title="Terminal">

 

```bash

keploy --version

```

 

</Command>

 

</Callout>

 

<Callout type="warning" title="Tests fail during replay">

 

First check whether PostgreSQL is running and whether the application is using the expected port and database configuration.

 

Then inspect the generated test report:

 

<Command title="Terminal">

 

```bash

find keploy/reports -type f | sort

```

 

</Command>

 

</Callout>
